# Working agreements

**Proposed.** How the founder, collaborators and agents work together day to
day. Shared at onboarding; changes go through the review queue.

## Purpose

Let a distributed team do deep work without constant meetings, while nobody
waits long for an answer and nothing confidential leaks.

## When it applies

All studio work by anyone, on any project.

## Roles

Operations — planning-workflow maintains this page. Everyone follows it. The
**founder** resolves exceptions.

## Inputs

The [tooling](../tooling.md) page and each project's brief.

## Steps

### Async first

1. Write it down: briefs, decisions, feedback and handoffs are written in the
   project's agreed channel, not only spoken.
2. A message should be answerable without a follow-up: context, the
   question, options, the deadline for an answer.
3. Meet when a decision needs live discussion, a critique benefits from
   showing, or a written thread has gone three rounds without converging.
   Every meeting has an agenda and ends with written decisions.

### Response times (working days)

| Channel | Expected response |
| --- | --- |
| Blocker flagged as urgent | Same working day |
| Project questions | Within one working day |
| Reviews requested in a brief | By the date in the brief |
| Client messages (studio response) | Within one working day, even if only to say when |

State your working hours and time zone; outside them nobody is expected to
answer. Flag absences a week ahead.

### Tools

Use only the tools named in [tooling](../tooling.md) and the project brief.
Client files stay in the vault and the client's agreed locations, never in
personal storage or public repositories.

### Confidentiality in daily work

- Codenames everywhere public or shared: commits, branch names, file names,
  issue titles, chat channel names.
- No client material in AI tools that may retain or train on it.
- Screenshots and recordings of client work are client material.

### Feedback

Critique the work against the brief and criteria, not the person. Name the
problem, its effect and, when you have one, a direction. Disagree in the
thread, then commit to the decision.

## Outputs

Written decisions in project channels; acknowledged agreements at onboarding.

## Quality gate

- [ ] Every decision is written where the project team can find it.
- [ ] Response times met, or a delay announced.
- [ ] No client identifier in any public or shared space.

## Metrics

Blockers older than one working day; meetings without written decisions.

## Failure modes

- Decisions made on calls and never written down.
- Urgent-by-default messages that erode deep work.
- Client names creeping into commit messages or file names.
