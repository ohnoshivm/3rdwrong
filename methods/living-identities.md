# Living identities

A living identity changes across time, context or input while remaining
recognisable and useful. Motion, interaction, generative or adaptive behaviour
is a design choice, not a default feature.

## When an extension is justified

Consider a dynamic capability only when it solves a stated communication or
use problem that a static rule cannot solve as well. The concept must explain
why the identity changes, what stays constant, who controls the change and how
it behaves when inputs are missing. Possible reasons include making a system's
logic visible, adapting information to a real context or giving feedback that
helps a person complete a task. Each reason is a project hypothesis until
validated in use.

## When it is not justified

Keep the identity static when movement or adaptation adds decoration, raises
production or access cost without a clear benefit, reduces recognition, or
requires a complex technical system the client cannot maintain. Do not use
motion to conceal weak logo construction or to make a route appear more
original. Complex 3D experiences are excluded from the standard Identity
System; a separately scoped extension or partner service would be required.

## Decision test

Before proposing a living element, answer all of these:

1. **Purpose:** What does the change communicate or help someone do?
2. **Concept link:** How does the behaviour express the approved idea?
3. **Invariant:** Which forms, values or rules keep the identity recognisable?
4. **Control:** What input changes the output, and who can change that input?
5. **Failure:** What happens with missing, invalid or extreme input?
6. **Access:** Can a person understand and use it with motion reduced, sound off,
   keyboard input or assistive technology where relevant?
7. **Production:** Can the client run, update and export it with available tools?
8. **Evidence:** Which claims are documented and which are hypotheses to test?

If the purpose, invariant, failure behaviour or maintenance owner is unknown,
do not include the feature in the approved system yet.

## Minimum motion principles in standard scope

The standard scope includes **key applications and motion principles**, not a
full interactive product or complex 3D experience. Where motion is relevant,
document:

- Purpose and trigger for each movement.
- What remains still and recognisable.
- Duration, pacing, direction and easing as design rules, with examples.
- Reduced-motion behaviour and a useful static equivalent.
- Sound expectations, if sound is part of the identity at all.
- Export formats, dimensions, loop behaviour and a fallback for unsupported
  environments when a deliverable file is agreed.
- A short usage example that demonstrates a repeatable principle.

Avoid unnecessary looping, flashing, rapid camera movement and motion that
blocks reading. Check motion in context and respect user and platform settings.
If production needs custom code, complex 3D or ongoing asset creation, scope it
separately.
