# 06 System

## Objective

Turn the identity elements into usable rules and test whether those rules hold across the applications agreed for the engagement.

## Required inputs

- The selected route, identity elements and applicable sign-off records.
- A written list of channels, formats, sizes, content and production constraints.
- The identity-system specification and application-testing matrix.

## Activities

1. Specify system invariants, variables, applications, digital rules, motion principles and exceptions; state hierarchy, layout, spacing, colour, type, imagery and asset-selection rules as decisions a user can repeat.
2. Build examples across several unlike applications: for example, a small label, line sheet, social crop and digital product page if in scope.
3. Test long and short names, dense and sparse content, small sizes, one-colour use and accessible contrast.
4. Check production realities such as print stock, emboss, foil, embroidery, screen use or vendor tolerances where relevant.
5. Identify which variations are allowed, which are exceptions and which elements must remain stable.
6. Revise the system when multiple applications reveal a rule that fails; do not patch every mock-up independently.

## Research methods

- Use application prototypes with representative content rather than decorative mock-ups.
- Test with actual dimensions, viewing distances and output conditions where feasible.
- Ask a colleague unfamiliar with the route to apply the rules to a new example.

## Deliverables

- A tested identity system specification and rules.
- A clear list of invariants, variables, applications, digital rules, motion principles and justified exceptions.
- Representative, in-scope applications with production notes.
- A defect and exception log linked to the test matrix.
- A visual sign-off candidate, not a claim of universal compatibility.

## Quality criteria

- At least three unlike applications are tested when scope permits; limits are explicit when it does not.
- A user can reproduce a new application without inventing missing rules.
- Typography, contrast, small-size performance and production constraints are checked.
- Exceptions have reasons and do not silently weaken core recognition.

## Common failure modes

- Testing only one hero mock-up.
- Using mock-up texture or lighting to hide poor contrast or weak geometry.
- Calling a system flexible when every application needs custom art direction.
- Ignoring vendor, screen or language constraints until delivery.

## Human approval

The client reviews applications against the approved strategy and the agreed test set. The authorised person gives **visual sign-off** separately from strategy approval. Any strategy change returns to phase 03; a production defect returns to the relevant system rule.

## Completion conditions

- Required application types have been checked or exclusions recorded.
- Critical defects are fixed or accepted as named exceptions by the client.
- The identity system is ready for validation and final delivery.
