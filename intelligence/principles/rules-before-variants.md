# Define the rule before multiplying variants

## Statement

**Interpretation** — Proposed principle: specify an invariant, permitted variables and the reason for
change before producing an application family. Variety becomes a system when another operator can make a
new output without inventing a new concept.

## Evidence

**Documented** — Whitney's studio account describes a toolbox for its in-house designers. DEMO's original
page describes variable type controlled by a script. [Whitney
source](https://www.jetset.nl/archive/whitney-museum-identity); [DEMO
source](https://studiodumbar.com/work/demo).

**Interpretation** — The [Whitney study](../projects/experimental-jetset-whitney.md) and [DEMO
study](../projects/studio-dumbar-demo.md) support comparing explicit rules across human interpretation
and software-controlled variation. They do not demonstrate that either model is universally superior.

## When it applies

**Hypothesis** — Use this question when the client genuinely needs repeated outputs with different
content, sizes or editions, and when an intended operator can be named.

## When it fails

**Interpretation** — A rule can be overcomplicated, aesthetically weak or unsuited to the client's
content. Consistent outputs do not by themselves make a valuable identity. One stable layout may answer a
limited need more effectively.

## How to test it in a project

**Hypothesis** — Give an unfamiliar operator the rule sheet and real unprepared copy. Ask for a new
small, dense and image-free application. Record needed interventions and invented exceptions.

**Hypothesis** — Compare the proposed system with a simpler fixed-template alternative. Reject or
simplify the rule if it creates repeated errors without a useful expressive or operational gain.

## What not to copy

**Interpretation** — Reuse the relationship between invariant and variation, never Whitney's line or
DEMO's lettering. A superficially similar output is not evidence that an original rule has been
developed.

## Application to 3RDWRONGS

**Hypothesis** — Use the client's actual product-name and language constraints to choose a rule. Start
with a static family, then test whether motion adds a needed behaviour rather than another decorative
variable.

## Evidence classification

### Documented

**Documented** — The cited creators describe selected system mechanisms; no comparable performance trial
was reviewed.

### Interpretation

**Interpretation** — The principle is a synthesis of selected references and could be biased towards
unusually well-documented work.

### Hypothesis

**Hypothesis** — An explicit grammar could improve independent operation. The operator comparison above
is the proposed local test.

### Unknown

**Unknown** — The useful complexity level, training cost and recognition effect for a new client remain
unmeasured.

## Open questions

- **Unknown** — Which variable is necessary, and which merely increases production choices?
- **Hypothesis** — Can the rule survive translated text without special rescue? Test before handover.
